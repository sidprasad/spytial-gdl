Lightweight interactive graphs (with semantics!)

Traditional graph description languages let you write a diagram as lightweight source and delegate its layout to a renderer. That delegation becomes a problem when spatial arrangement itself carries meaning, because the renderer can place elements in ways that contradict it. Spytial GDL pairs a simple graph description language with spatial requirements.

Describe the graph, then state relationships, such as orientation and grouping, that every valid layout must preserve.

%% An illustrative tic-tac-toe position. The dot is an empty cell. %% The edges describe the board, not the order of moves. a[X]:::Cell -> b[O]:::Cell : right b -> c[X]:::Cell : right d[·]:::Cell -> e[O]:::Cell : right e -> f[·]:::Cell : right g[O]:::Cell -> h[X]:::Cell : right h -> i[X]:::Cell : right a -> d : below d -> g : below b -> e : below e -> h : below c -> f : below f -> i : below @orientation(selector=right, directions=[directlyRight]) @orientation(selector=below, directions=[directlyBelow])

The edges already say right and below. The layout should mean it. These two requirements keep the cells in their rows and columns, even when you drag them.

@orientation(selector=right, directions=[directlyRight])
@orientation(selector=below, directions=[directlyBelow])
See the same graph in Mermaid

In a Mermaid flowchart, right and below are edge labels, not layout requirements. A flowchart direction applies to the graph, not separately to each relation.

Mermaid source

This is Mermaid 11.12.0 with its default flowchart layout and flowchart TB. It has the same cells, labels, and edges as the board above. Mermaid also has block diagrams for explicitly arranging a grid; this example compares labeled flowcharts.

Explicit requirements on layout enable interaction beyond rendering: constrained rearrangement, explanations for contradictory requirements, and direct manipulation that edits the underlying graph while preserving the diagram's spatial meaning.
